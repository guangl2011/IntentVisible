Buyer Intent Lib — Core Intent Engine

The first build package for a standalone, Visible-independent intent intelligence infrastructure: Intent Schema v1, a Solix golden dataset, URL-to-Brand/Product modeling, and an evidence-first LLM intent generator with a minimal API.
BIL's bet, from the product plan: a brand's public website and product pages already contain the semantics of purchase intent — category questions, comparison moments, scenario needs, risk objections. Today that semantics is trapped in prose. BIL extracts it into a versioned, machine-callable intent library that entertainment-affiliate matching and advertising-diagnosis systems can query, without requiring any user-behavior tracking or the Visible GEO-monitoring product.

This spec covers the first build package only — the plan's designated first Autobuild task: Intent Schema + Importer + URL-to-Intent Generator in standalone generation mode. Shopify App, entertainment matching, and the diagnosis Skill are later packages and are named here only as boundaries they must not break.

The decision to approve

Build the core intent engine as a TypeScript monorepo inside the registered guangl2011/IntentVisible repo (currently empty), shipping: Intent Schema v1 as JSON Schema + TypeScript types; a Solix golden dataset and importer; a URL extractor that produces evidence-cited brand/product profiles; an LLM intent generator in standalone mode (visibility_pct = null, measurement_status: not_measured); and the minimal async API surface (/v1/brands/analyze, /v1/products/analyze, intent reads, /v1/jobs/{id}).

What makes this hard

The failure mode named in the plan is not "the LLM writes bad prompts" — it is confident fabrication presented as measurement: invented search volumes, pseudo-visibility scores, product claims with no page evidence. The architecture must make fabrication structurally difficult: measurement fields are schema-nullable and pipeline-forbidden, every generated intent carries evidence_urls, and every claim is traceable to a fetched snapshot.

In standalone mode the pipeline cannot emit visibility_pct, monthly_search_volume, or any measured value: these fields are null with measurement_status: "not_measured", and the schema validator rejects any generated record that sets them. Real measurement enters later through the optional Visible adapter — never as a dependency. User-behavior pixels, cross-site personal profiles, GEO visibility measurement, ad-bidding, affiliate settlement, the Shopify App, the entertainment matching adapter, and the landing-page diagnosis Skill. Each is a later package; this spec delivers only the engine they consume.

Two plan-level optimizations I'm carrying into the spec (both reversible, both flagged where they appear):

  1. Persistence: the plan names PostgreSQL. For the first package I'm specifying Drizzle ORM against PostgreSQL-compatible SQL with tests runnable on SQLite, so the coder sandbox needs no database service and the swap to hosted Postgres is a connection string. If CI can provision Postgres, drop the SQLite test profile.
  2. Incremental refresh: the plan requires partial regeneration when a PDP changes (§3 M3) but defers the mechanism. This package adds a content_hash per fetched page snapshot now — it's a one-line schema field that later makes "regenerate only what changed" possible without a migration.

Data contract: the Intent record

The canonical record, from the plan's §4.1 example, tightened with the plan's §2.1 field adjustments. The two measurement fields and their companions are the load-bearing part — the schema, the engine, and CI all enforce them.

{ "schema_version": "1.0.0", "intent_id": "int_camping_fridge_runtime", "intent_version": 1, "scope": "product", "brand_id": "brand_solix", "intent_name": "Camping Fridge Runtime", "buyer_stage": "Solution Research", "intent_category": "Technical", "persona": "Camper/Overlander", "pain_point": "Need realistic runtime for a camping fridge", "country": "AU", "language": "en", "prompts": ["Which portable power station can run a camping fridge overnight?"], "recommended_content": "Runtime guide with appliance assumptions", "recommended_cta": "Check compatible models", "sku_ids": ["sku_example_01", "sku_example_02"], "evidence_urls": ["https://example.com/products/example"], "generation_method": "llm_with_page_evidence", "generation_model": "…", "measurement_source": null, "measurement_status": "not_measured", "visibility_pct": null, "monthly_search_volume": null, "confidence": "medium" }
  • confidence is an enum (low|medium|high) scoring evidence support for the record — never a conversion prediction.
  • measurement_status is enum not_measured|imported|measured; only imported/measured records may carry visibility_pct or monthly_search_volume. A Zod superRefinement enforces the pairing; the generator can only ever construct not_measured records.
  • intent_version is an integer bump per regeneration; intent_id survives rewording via semantic dedup, so re-runs update rather than duplicate.

TypeScript ESM monorepo (pnpm), LLM orchestration in TypeScript behind a provider-agnostic adapter interface (no SDK lock-in in engine code), Drizzle ORM with Postgres dialect for production and SQLite for local tests, Fastify for the API, BullMQ-style queue with an in-process fallback for tests, Vitest everywhere. Object storage behind a local-filesystem driver in tests.

The engine's core path, with the two failure branches that matter most: fetch-denied and validation-failed. Every artifact that flows downstream carries the evidence it was derived from, so an intent can always be traced back to the snapshot it came from.

Incremental refresh arrives later, but the foundation is in this package: re-running analyze on an unchanged PDP (same content_hash) skips regeneration; a changed hash regenerates that page's intents and bumps versions, leaving other pages' intents untouched.

Verification is mostly machine-checkable — that is the point of an evidence-first engine. Plan §9.1's pilot metrics (≥80% human-review usability, ≥90% SKU coverage, 3–5 merchants installed) are not acceptance criteria here: they need real merchants and human panels, which come after this package ships.

No production credentials in CI or code — the LLM key enters as a runtime secret, never a fixture. Crawler obeys robots.txt and per-domain rate caps by default. Generated content must never assert facts absent from page evidence; the validator drops such records and logs them.
  • Standalone mode is the only generation mode in this package. Generated records are not_measured with null visibility and volume; enforcement is schema-level, not convention.
  • Repo home: build in guangl2011/IntentVisible, monorepo rooted at the repo top, per the assumption recorded in Current State.
  • Solix inheritance list is normative (plan §2.1): the eleven listed fields carry over; measurement-derived fields (visibility_pct, source_models, observed_at, monthly_search_volume, revenue_expansion/market_expansion) do not — they exist only for imported/measured records, and opportunity_type: hypothesis is the standalone-mode substitute.
  • Schemas change only in dedicated PRs (plan §10 principle 3) — matching and diagnosis packages consume this schema, never edit it incidentally.
  • Architecture stack as specified in What We Build: TypeScript ESM monorepo, provider-agnostic LLM adapter, Drizzle (Postgres prod / SQLite test), Fastify, queue with in-process test fallback, Vitest.
  • No user-behavior tracking, no pixels, no personal profiles anywhere in the pipeline — public page content and authorized catalogs only.

These decisions are excluded from re-litigation during planning and implementation. If the upstream plan changes, they change through a spec revision, not a coder's judgment call.
